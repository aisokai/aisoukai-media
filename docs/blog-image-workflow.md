# 記事に合う画像がないときの手順

先生の2026-09-20指示に基づく、ブログ画像の手動運用。

1. 記事の主題・本文と既存画像の実物を確認する。登録枚数、広いカテゴリ、タグだけで適合と判断しない。同一ファイルの重複登録や、他記事への使い回しも確認する。
2. 適した画像がなければ未設定にし、対象記事・不足する表現・必要な構図を先生に報告する。関係の薄い画像を当てはめない。
3. 先生が指示する別の画像生成タスクで作成する。この手順を理由に自動でタスクを起票したり、画像生成APIを呼んだりしない。
4. 生成タスクで `public/images/library/<category>/` に保存する。既存ファイルを上書きせず、保存先・形式・寸法・SHA-256・生成元タスクを報告する。
5. 適用側で実画像と本文を照合する。図の形状・医療表現・利用条件・既存使用との重複を確認し、合わなければ再生成または不足として報告する。説明用の模式図を実写真や正確な診断図と扱わない。
6. 対応する記事だけへ画像と内容に合うaltを設定する。本文・元の日付・topic IDを保持し、画像変更前の承認を新しい版へ流用しない。旧承認情報・履歴は保持し、変更版は再審査まで下書きとする。
7. 対象限定の差分確認、検証と独立レビューを行う。同期・公開はそれぞれ既存の承認・審査手順に従う。画像適用の許可を記事公開の承認と解釈しない。

## MWFでの扱い

`scripts/lib/mwf-images.mjs` は `data/image-library.json` の明示的な `topic_assignment` だけを参照する。topic IDと記事タイトルが一致し、実画像を確認した記録があるものに限る。カテゴリや先頭候補へのフォールバックはない。

- `topic_assignment`: `topic_id`、`title`、`status: visually_matched`、確認記録の `evidence` と対象 `article_path`。
- `content_sha256` と `git_blob`: 確認した実ファイルの識別子。実行時は同じリビジョンのライブラリとGitツリーで、通常ファイルの存在・Git blobの一致を確認する。
- `license_status`、`license_source`、`license_note`: 分かっている利用根拠を正直に記録する。先生提供の生成物というだけで、他の素材も含めて `approved` にしない。
- `draft_use_authorization`: 先生が具体的な生成画像の下書き適用を指示した場合の、topic ID・SHA-256・指示の根拠。これは用途限定の下書き適用許可であり、画像利用条件の独立確認や公開許可を代替しない。

候補なし、題名不一致、複数候補、同じ画像の重複登録、利用根拠不足、ファイル欠落・変更、取得失敗は、画像を未設定のまま `image_selection_status: missing` と理由を記事ヘッダに残す。新規生成した下書きの既存レビュー依頼には「画像不足」を添える。通知先・通知回数は増やさない。既存の古い記事や復元記事にこのマーカーがない場合まで、通知上で不足を確認済みと断定しない。

選べた画像も `assigned_pending_review` であり、生成後の本文との一致は記事審査で確認する。画像ライブラリに登録済みでも、他のtopicへの転用は新たな確認が必要となる。
